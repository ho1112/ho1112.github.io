## 🔥 今週の主要テーマ
今週は「フロントエンドのパフォーマンスと構造の見直し」が中心でした。GitHubはCSS-in-JSを取り除いてCSS Modulesへ移行し、SSR時間を大幅に短縮しました。AnthropicはClaude Webアプリのtime-to-typeableを3.1秒から0.55秒に短縮した過程を公開しました。過度な抽象化が開発者とAIエージェントの双方にとってコストになるという計測結果も出ています。一方で、Vite+ 1.0、Cloudflareのcf CLI、EmDash 1.0など、ツールのエコシステムも急速に動いています。

## 1. 🔍 深掘り
- **[Improving Site Performance by Shipping More CSS](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)** (出典: *Frontend Focus #760*)
	![Improving Site Performance by Shipping More CSS 代表画像](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/wqdeehcjo7y0imo6gazv.jpg)
	- 背景: GitHubは3年かけてgithub.comからstyled-componentsとCSS-in-JSを取り除き、CSS Modulesへ移行しました。
	- 主な機能: CSSはむしろ多く配信するようになりましたが、サーバーサイドレンダリング時間が55%短縮されたと報告しています。CSS Modulesはブラウザ標準ではなくバンドラーの慣習で、`.module.css`ファイルのクラスを一意な名前に書き換えてファイル単位でスタイルを分離し、ランタイムコストがありません。
	- 実務での活用: CSS-in-JSのランタイムがSSRパフォーマンスの負担になっているサービスで、移行を検討する根拠として使えます。同じ記事がJavaScript Weekly #804でも紹介されています。
	- 注意事項: 3年かかった大規模な移行である点から、段階的な移行戦略が必要です。詳細な制約は原文での確認が必要です。
- **[The Grand Unifying Architecture of Frontend](https://dev.to/playfulprogramming/the-grand-unifying-architecture-of-frontend-bhk)** (出典: *JavaScript Weekly #804*)
	![The Grand Unifying Architecture of Frontend 代表画像](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/q97l6jlstbu4nz3us8ex.jpg)
	- 背景: HTMX、React、LiveViewなどのフレームワークがバラバラに見える理由を、ひとつの視点で説明しようとする記事です。
	- 主な機能: SolidJSの創始者Ryan Carniatoは、これらのツールはナビゲーション、コンテンツ、即時的なUIフィードバックという3つの仕事をクライアントとサーバーの間でどう分担するかが違うだけだと主張します。続けて、Solid 2.0がこのスペクトラム全体を扱おうとしていると説明します。
	- 実務での活用: フレームワークを選ぶ際、機能一覧の代わりに、この3つの責務がどこに置かれるかを基準に比較できます。
	- 注意事項: Solid 2.0に関する内容は、著者が自分のフレームワークを説明する視点である点を考慮する必要があります。

## 3. 📝 おすすめ記事 & チップ
- **[Detect When Elements Overlap with CSS](https://ishadeed.com/article/css-detect-overlap/)** (出典: *Frontend Focus #760*)
	![Detect When Elements Overlap with CSS 代表画像](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/v1790768407/sqfroq51wfjasopm9vyc.png)
	+ 主要なインサイト: アンカーポジショニング、スタイルコンテナクエリ、スクロール駆動アニメーションを組み合わせ、JavaScriptなしで2つの要素が重なる瞬間を検出します。はみ出す「measure」要素をトリガーとして使います。
- **[From 1,256ms to 96ms: Fixing INP in a massive React dropdown](https://reactdigest.net/links/23356/56924fb8-2fd8-4d90-9539-8cdfc1099755/web)** (出典: *React Digest #576*)
	+ 主要なインサイト: オプション1,175個をすべてレンダリングしていたドロップダウンのINPは1,256msでした。小さなカスタム仮想化フックで表示される行だけをレンダリングし、DOMを13個に減らしてINPを96msまで下げました。
- **[Optimizing Objects with null Prototypes](https://adventures.nodeland.dev/archive/optimizing-objects-with-null-prototypes/)** (出典: *JavaScript Weekly #804*)
	+ 主要なインサイト: V8では`{ __proto__: null }`や`Object.create(null)`で作成したオブジェクトは、遅いディクショナリモードで始まります。通常のオブジェクトを作成してからプロトタイプを`null`に設定すると、高速なプロパティが維持されます。

## ✍️ おわりに
今週のニュースを一言でまとめると「測って、取り除く」です。GitHubのCSS Modulesへの移行もClaude Webアプリのパフォーマンス改善も、目新しい技術ではなく、ボトルネックを計測して不要なレイヤーを取り除いた事例でした。抽象化のコストがAIエージェントのコストとしても現れるという計測結果は、コードの読み手が人間からエージェントへと広がっていることを示しています。仮想化フック1つでINPを1,256msから96msに下げた事例も同じ文脈にあり、複雑な解決策よりも先に、レンダリング対象を減らせないか確認する習慣が有効だと思います。子ども向けデザインのように、ユーザーを設計プロセスに直接参加させるアプローチは、パフォーマンス最適化とは異なって見えても、実際の利用文脈から出発するという点で通じていると感じました。
