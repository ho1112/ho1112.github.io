## 🔥 今週の主要テーマ

今週は「JavaScriptで作っていたものをプラットフォームに任せる」という流れが随所に見られました。React AriaのSheetはCSS scroll snapとview timelineだけでスワイプジェスチャーを実装し、CSS Anchor Positioningはツールチップの位置計算をJSから取り除きます。一方、Next.js 16.4はCache Componentsを公式の推奨モデルに引き上げ、エージェントベースのアップグレードツールを発表し、Smashingはデザインシステムを AIが読める形にする方法を取り上げました。Remix 3.0の脱ReactやDenoのCloudflare合流のように、フレームワークとランタイムの勢力図が再編されるニュースも続きました。

## 1. 🔍 深掘り
- **[React Aria's New Swipeable Sheet and the CSS Tricks Behind It](https://react-aria.adobe.com/blog/sheet)** (出典: *React Status #493*)
   - 背景: ボトムシートのようなスワイプ式オーバーレイは、これまでJSのタッチイベントで実装するのが一般的でした。React Ariaチームはこれをやめ、スクロールそのものをジェスチャーエンジンとして使う方式を選びました。
   - 主な機能: ビューポートの高さの2倍のスクロールコンテナの中にシートを置き、開いた位置と閉じた位置にscroll snapポイントを設けます。スワイプの進行度に合わせたアニメーションは`view-timeline`で連携させ、部分的に開くsnap pointsは1pxのマーカー要素と`scroll-margin-top: 100dvh`で実現します。シートのスタックは`timeline-scope`と`animation-composition: accumulate`で処理します。
   - コード例:
```css
     .sheet {
       view-timeline: --sheet;
       view-timeline-inset: 0 100dvh;
     }
     .backdrop { animation-timeline: --sheet; animation-range: entry; }
```
   - 実務への適用: スワイプがメインスレッドの外でディスプレイのリフレッシュレートで動作し、ネイティブのモメンタムやラバーバンディングの物理挙動が無料で付いてきます。`position`、`swipeDirection`、`snapPoints`、`preventDismissal`といったpropsで、方向や動作を調整できます。
   - 注意事項: iOSのソフトウェアキーボードでは動的ビューポート単位が反応しないため、コンテンツに`padding-bottom: calc(100dvh - var(--visual-viewport-height))`を別途指定する必要があります。
- **[Next.js 16.4 Makes Cache Components the Recommended Default](https://nextjs.org/blog/next-16-4)** (出典: *React Status #493*)
   - 背景: 16.xの間、App Routerの暗黙的なキャッシュに代わるCache Componentsモデルが発展してきました。一部のケースでは従来のモデルと同じコスト・パフォーマンスの保証が難しく、広くは推奨できませんでしたが、16.4でそのギャップが埋まりました。
   - 主な機能: `'use cache'`はコンポーネント単位のCache-Controlに相当し、1つのページの中で静的シェルとリクエスト時のレンダリングを混在させられます。16.4には、ルートのシェル・プリフェッチ・ナビゲーションが静的であることを保証する`ensureStatic`と、プリフェッチからキャッシュコンテンツを除外する`navigation()`・`prefetch()`が追加されました。
   - コード例:
```jsx
     async function Projects({ userId }) {
       'use cache';
       cacheLife('hours');
       // DB取得後にレンダリング
     }
```
   - 実務への適用: `create-next-app`で作成した新規アプリでは、Cache Componentsがデフォルトで有効になります。既存アプリは`npx next@canary upgrade --agent=latest`で、エージェント向けのマイグレーションガイドとcodemodを入手できます。開発環境ではTurbopackのディスクキャッシュが20〜25%減り、React 19.3も含まれます。
   - 注意事項: Cache ComponentsはNext.js 17でデフォルトになる予定です。エージェントフィードバックやRust製React Compilerなど一部の機能は、まだexperimentalフラグの裏側にあります。

## 3. 📝 おすすめ記事 & チップ
- **[CSS Does Your Tooltip Positioning Now](https://allthingssmitty.com/2026/10/05/css-does-your-tooltip-positioning-now/)** (出典: *Frontend Focus #761*)
  + 背景: ツールチップやポップオーバーの位置を`getBoundingClientRect()`で計算すると、ウィンドウサイズの変更、スクロール、ビューポート下端からのはみ出しのたびに、リスナーと補正ロジックが必要でした。
  + 主要なインサイト: `anchor-name`と`position-anchor`で2つの要素を結び付けると、ブラウザが位置を継続的に再計算します。`position-try-fallbacks`ははみ出したときに反対側へ反転させ、`popover`属性と併用すればJSなしでドロップダウンになります。`anchor-size(width)`でドロップダウンの幅をボタンに合わせることもできます。
  + コード例:
```css
    .term { anchor-name: --my-anchor; }
    .note {
      position: fixed;
      position-anchor: --my-anchor;
      position-area: bottom;
      position-try-fallbacks: flip-block, flip-inline;
    }
```
  + なぜ役立つか: 位置の問題と表示タイミングの問題を切り分けて整理してくれます。anchor positioningは「どこに」置くかだけを解決し、「いつ」表示するかは`:has()`やpopoverが担います。アンカーの関係はあくまで視覚的なものでスクリーンリーダーの助けにはならないため、アクセシビリティ機能と取り違えないようにという警告も、実務では重要です。
- **[Why Don't More Developers 'Use the Platform'?](https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/)** (出典: *JavaScript Weekly #805*)
  + 背景: プラットフォーム支持派だったNolan Lawsonが、あえて反対側の立場から「なぜ人々はブラウザの機能があるのに自分で作るのか」を分析します。[Hacker Newsでも長い議論](https://news.ycombinator.com/item?id=49950554)が行われました。
  + 主要なインサイト: 理由としては、ブラウザがエコシステムを追いかけていた歴史、npmライブラリがもたらす親しみやすさとドキュメント、CSSの難解さが挙げられています。それ以上に、自分で作るほうが楽しく、IKEA効果まであるという点が核心です。モーダルを自作しながらフォーカストラップまで学ぶ過程が学びになる、というわけです。AIコーディングがこれを減らすのか増やすのかについては、楽観と悲観の両方のシナリオを提示しています。
  + なぜ役立つか: 同僚やチームの「自前実装」志向を、非難するのではなく理解する視点を与えてくれます。本人のClickHouse圧縮の経験談が、プラットフォームに任せたほうがよい事例として説得力があります。
- **[Expose Your Design System To AI](https://www.smashingmagazine.com/2026/06/how-make-design-system-ai-ready/)** (出典: *Smashing Newsletter #579*)
  ![How To Make Your Design System AI-Ready](https://mcusercontent.com/16b832d9ad4b28edf261f34df/images/2692e8dd-ee96-5341-e05a-735c498ad834.png)
  + 背景: AIが一貫した結果を出すには、明確な決定と原則が必要です。人間は経験で抜けを埋めますが、AIは推測で埋めるためです。
  + 主要なインサイト: Vitaly Friedmanのガイドは、デザインシステムをAI-readyにするためのヒント、ツール、事例を収めています。ドリフトを減らしコンテキストを維持する方法は、Hardik Pandyaの[LLMが消費できる形式に再構成する方法](https://hvpandya.com/llm-design-systems)でさらに詳しく読めます。
  + なぜ役立つか: デザインシステムを人間向けのドキュメントから、機械が読める仕様へと拡張していく方向性を、具体的な資料とともに示してくれます。

## ✍️ おわりに
今週のニュースを読みながら、「自分で作る楽しさ」と「プラットフォームに任せる効率」のバランスをあらためて考えました。React Ariaがスクロールとview timelineだけでシートを実装した事例は、プラットフォームの機能が十分に成熟したことを示しています。一方で、Nolan Lawsonが指摘するように、AIエージェントがコードを書く時代には、プラットフォームに任せるかどうかを判断することが、ますます開発者の役割になっていきます。Next.jsのエージェント向けアップグレードツールやAI-readyなデザインシステムの議論も、同じ方向を向いていました。ツールがコードを書く速度が上がるほど、明確なコントラクトとガードレールを設計する力がより重要になると考えています。
