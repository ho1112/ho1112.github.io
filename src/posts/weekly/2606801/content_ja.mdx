## 🔥 今週の主要テーマ

今週は「**エンジン交換**」が貫く一週間でした。Anders Hejlsbergが自ら実演した**TypeScript 7のGoネイティブコンパイラ**（10倍速）、そして**TanStackが自社サイトからRSCを取り除いたアーキテクチャの決定**が、フロントエンドの議論の中心に立ちました。CSS方面では`conic-gradient()`の驚くべき活用法や`infinity`定数の話が、ツールエコシステムでは「Rustは依然としてJavaScriptを侵食し続けている」という話題が続きました。さらにSmashingが紹介した愛らしい小規模Webプロジェクトまで、実務とインスピレーションを幅広く満たした一週間でした。

## 1. 🔍 深掘り
- **[Why TanStack Stopped Using RSC on Its Site](https://tanstack.com/blog/we-stopped-using-rsc-on-tanstack-com)** (出典: *React Status #485*)
  - 背景: TanStackはもともと、重いマークダウン・構文ハイライトレンダラー（Shikiベース、約358KB）をクライアントに送らないようにするためReact Server Componentsを導入していました。RSCはサーバーでコンテンツをレンダリングしてFlightペイロードだけで届けるため、初期クライアントバンドルが大きく減るという実質的なメリットがありました。
  - 主な機能: ところが、ハイライト・マークダウンスタックそのものを27KBレベルまで削減したところ、計算が逆転しました。小さなライブラリなら、リクエストごとにサーバーでレンダリングしてRSC/Flightペイロードを送るよりも、小さなライブラリを一度だけクライアントに送って何度もレンダリングするSSR方式の方が優れているというのです。そのためTanStackは、意図的に小さく作った2つのライブラリ**TanStack Markdown**（4.9KB）と**TanStack Highlight**（8KB、25言語）を新たに作りました。
  - コード例:
```txt
    # RSC方式: サーバーでマークダウン/ハイライトをレンダリング → Flightペイロードで送信
    #           重いレンダラーをクライアントに送らない代わりに、ページごとにサーバー往復

    # SSR + 小型ライブラリ (TanStackの新しい選択)
    #           TanStack Markdown(4.9KB) + Highlight(8KB)を「一度だけ」送信
    #           以降のルート遷移はクライアントで繰り返しレンダリング → ブロッキングタイム↓、コード単純↑
```
  - 実務への適用: 「RSCかSSRか」はイデオロギー対決ではなく、**依存関係のサイズによって変わるトレードオフ**であることを示す事例です。重いレンダラーをサーバーに隔離する必要があるならRSCが、レンダラーが十分に小さいなら「一度送って何度もレンダリング」するSSRが有利です。
  - 注意事項: このサイトはRSC除去以降も通常のプロダクション作業が併せて反映された状態なので、「純粋なRSC-only実験」ではありません。著者本人も、すべてのバイト削減をRSC除去の効果に帰するわけではないと明言しています。また、新しいライブラリはまだalpha段階です。
- **[The Creator of TypeScript Shows Off TypeScript 7](https://www.youtube.com/watch?v=OytpXXeNmTQ)** (出典: *JavaScript Weekly #796*)
  ![TypeScript 7を実演するAnders Hejlsberg](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/c_crop,g_south,w_w,h_h_sub_50/bjd0nutn9yncyimrgifx.jpg)
  - 背景: 14年間、TypeScriptは自分自身(TS/JS)で書かれたコンパイラを使ってきましたが、シングルスレッドのJavaScriptランタイムの限界にぶつかりました。Hejlsbergのチームは、コンパイラ全体を**Goへポーティング**してこのボトルネックを解消しました。
  - 主な機能: 動画でHejlsbergは、VS Codeの130万行のコードベースで新しいGoベースのコンパイラが生み出す**10倍の速度向上**を実演します。型チェックロジックを新たに発明したわけではなく、TypeScript 6.0と同じ構造・ロジックを維持したままGoで書き直したため、エラー・メッセージ・位置が2つのコンパイラ間で同一です。新しい**LSP**(Language Server Protocol)言語サーバーも併せて導入されます。
  - コード例:
```bash
    # 既存のtypescriptの代わりにRCチャンネルをインストール → tscがまもなくGoネイティブバイナリに
    npm install -D typescript@rc

    # 型チェックのみ実行 (ビルドはesbuild/SWC/Viteが担当する構成が一般的)
    npx tsc --noEmit

    # 最新のナイトリー(バイナリ名tsgo)が欲しい場合は
    npm install -D @typescript/native-preview
```
  - 実務への適用: ほとんどの成熟したチームは、すでに`tsc`をビルドではなくCIの型チェック用途で使っています。TypeScript 7は、パイプラインで最も遅く、長く待たされていたこの段階を、一晩にして10倍速くしてくれます。
  - 注意事項: Vue、MDX、Astro、Svelte、Angularのように、コンパイラをプログラマティックAPIとして埋め込んで使うツールは、APIがまだ安定化されていないためTypeScript 7のメリットを完全には享受できません。これらは当分の間TypeScript 6に留まる必要があります。

## 3. 📝 おすすめ記事 & チップ
- **[When You Need To Make a Triangle, Think Conic Gradients](https://master.dev/blog/when-you-need-to-make-a-triangle-think-conic-gradients/)** (出典: *Frontend Focus #752*)
  ![conic-gradientで作った図形の例](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/bhdcsf1wb2njno2mhf3s.jpg)
  + 主要なインサイト: `conic-gradient()`は思っている以上に柔軟です。パイのスライス、放射状の光線(ray burst)、三角形まで作ることができ、トランジションも適用できます。画像アセットなしで純粋なCSSだけで図形を描ける点が、実務で大きなメリットです。
```css
    /* 右上が切り取られた直角三角形 (例) */
    .triangle {
      width: 200px;
      aspect-ratio: 1;
      background: conic-gradient(from 90deg at 0 0, transparent 25%, tomato 0);
    }
```
- **[Your SPA is Leaking Memory: 'Soak Test' It](https://denodell.com/blog/your-spa-is-leaking-memory-soak-test-it)** (出典: *React Status #485*)
  + 主要なインサイト: SPAのメモリリークは、ユーザーが遭遇する前に捕まえるべきです。一つのブラウザコンテキストでPlaywrightフローを繰り返し実行し、**DOMノード数とイベントリスナー数**を追跡すれば、リークを早期に発見できます。
```js
    // 同じコンテキストで同一フローを繰り返し、ノード数の増加を観察
    for (let i = 0; i < 50; i++) {
      await page.goto("/dashboard");
      await page.getByRole("button", { name: "Close" }).click();
      const nodes = await page.evaluate(() => document.querySelectorAll("*").length);
      console.log(`iteration ${i}: ${nodes} nodes`);
    }
```
  + なぜこの記事が有益なのか: リスナーを適時に解放しなかったり、クロージャに参照が残ったりといったリークは、プロファイラで一度見ただけでは見逃しやすいものです。「繰り返した後にノード数が増え続けているか」という単純な指標は、回帰テストとして自動化するのにも適しています。
- **[Handling Concurrency on the Web with Web Locks API](https://tech.olx.com/handling-concurrency-on-the-web-with-web-locks-api-163b7e07eddd)** (出典: *Frontend Focus #752*)
  + 主要なインサイト: 複数のタブが同じ処理(例: トークン更新、アウトボックス同期)を同時に実行して競合する問題を、広くサポートされている**Web Locks API**で直列化する実践ガイドです。
```js
    // 複数のタブが同時に同じ処理を実行しないよう直列化
    await navigator.locks.request("sync-outbox", async (lock) => {
      await flushPendingRequests();
    }); // コールバックが終わるとロックが自動的に解放される
```
  + なぜこの記事が有益なのか: マルチタブ環境での重複リクエスト・レースコンディションは、再現が難しいバグです。別途のインフラなしにブラウザ標準APIだけで解決できる点で、実務適用のハードルが低いです。

## ✍️ おわりに

今週のニュースを貫く流れを一言で要約すると、成熟したエコシステムが「基本エンジン」を再び手入れし始めたという点です。TypeScriptは言語文法をほとんど変えずにコンパイラを丸ごとGoへ移し、TanStackはかつて正解のように思われていたRSCを状況に合わせて取り除きました。両事例とも「新しい技術を無条件に採用する」のではなく、**依存関係のサイズと実際のボトルネックを測定した上で決定する**という共通点を示しています。RSCかSSRか、RustかGoかといった論争も、結局はイデオロギーではなくプロファイリング結果の上で語るべきだということを、改めて確認させられます。

同時に、`conic-gradient()`で三角形を描いたり、Web Locks APIでマルチタブの競合を解決したりするように、すでに広くサポートされているプラットフォーム機能を改めて見直す記事が多かった点も印象的です。華やかな新規フレームワークと同じくらい、手にしている標準ツールをどれだけ深く知っているかが生産性を分ける時期だという気がします。
