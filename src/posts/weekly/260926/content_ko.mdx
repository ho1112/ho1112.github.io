## 🔥 이번 주 핵심 테마
AI 에이전트가 코드를 쏟아내는 시대에 맞춰, 성능과 품질을 지키는 방법을 다시 묻는 한 주였습니다. React-Redux는 시그널 기반 selector로 dispatch 비용을 줄이려 하고, GitHub Copilot 앱은 100만 줄 PR을 React 밖에서 렌더링하며, Linear는 CI 비용을 다시 설계했습니다. 데스크톱 앱은 tinyjs처럼 6MB대로 작아지고, 브라우저는 Safari 27과 Chrome이 네이티브 기능을 빠르게 늘리고 있습니다. 한편 Next.js의 치명적인 RCE 수정과 공급망 공격 소식은 보안 점검의 필요성을 다시 일깨웁니다.

## 1. 🔍 심층 분석
- **[Rendering Huge Pull Requests in the GitHub Copilot App](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)** (출처: *React Status #492*)
  ![Rendering Huge Pull Requests in the GitHub Copilot App](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/wurtgptbln8tma7ldkus.jpg)
   - 배경: 리팩터링이나 마이그레이션은 하나의 PR로 합쳐야 할 때가 있고, 리뷰 대화가 붙을수록 PR은 더 커집니다. GitHub 팀은 2,200개 파일, 100만 줄 이상의 변경, 400개가 넘는 인라인 코멘트가 있는 PR을 기준으로 Copilot 앱의 diff 화면을 다시 만들었습니다.
   - 핵심 기능: 코드 행은 높이를 미리 계산할 수 있으므로 가상화, typed array 기반 오프셋 계산, React 컴포넌트 없는 imperative 행 렌더러로 처리합니다. 반면 코멘트는 렌더링해 봐야 높이를 알 수 있어서 높이 계산을 두 영역으로 나눴습니다. 코드 지오메트리는 정확값이 고정이고, 동적 블록(리뷰 스레드, 답글 입력창 등)은 추정 후 측정으로 보정합니다. 측정은 블록마다 ResizeObserver를 두는 대신 스크롤이 멈춘 뒤 뷰포트 약 2400px 안쪽 블록만 한 번에 읽는 방식이고, 보정 시에는 사용자가 보던 행이나 블록을 기준으로 스크롤 위치를 유지합니다.
   - 코드 예제:
```text
     total height = deterministic code height          (exact, known up front)
                  + Σ dynamic block effective heights   (estimated, then measured)
                  + scroll padding
```
   - 실무 적용: 높이를 예측할 수 없는 콘텐츠가 섞인 가상 리스트(채팅, 댓글 스레드, 피드)에서 "확정 높이"와 "측정 높이"를 별도 인덱스로 분리하는 설계를 참고할 수 있습니다. 글에서는 자체 상태를 점검하는 구조화된 프로브를 화면에 상시 두고, 합성 대형 PR 픽스처로 E2E 예산을 검증하며, 변경, 측정, 개선 루프를 자동화한 과정도 소개합니다.
   - 주의사항: 옵저버가 자신이 관찰하는 요소의 레이아웃 높이를 직접 갱신하면 피드백 루프가 생깁니다. 또한 "사용자가 스크롤 중인가"를 판별할 때 화면이 스스로 일으킨 스크롤(사이드바 토글 후 재배치 등)과 구분하지 않으면 보정이 건너뛰어져 보던 위치가 밀립니다.
- **[The Root Scroller and How Not to Lose It](https://polypane.app/blog/the-root-scroller-and-how-not-to-lose-it/)** (출처: *Frontend Focus #759*)
   - 배경: root scroller는 뷰포트의 스크롤 컨테이너로, 스크롤 복원과 모바일 주소창 접힘 같은 브라우저 기능을 담당합니다.
   - 핵심 기능: 흔히 쓰는 CSS 패턴이 스크롤을 다른 요소에 넘기면 이런 기능이 사라진다는 점을 데모로 보여줍니다.
   - 실무 적용: 레이아웃을 `height: 100%`와 내부 스크롤 컨테이너로 구성하는 앱이라면, 뷰포트 스크롤을 잃고 있지는 않은지 점검해 볼 만합니다.
   - 주의사항: 스크롤 컨테이너를 바꾸는 CSS를 도입할 때는 스크롤 복원과 모바일 주소창 동작이 함께 깨지지 않는지 확인해야 합니다.

## 2. 🛠️ 툴 & 라이브러리
- **[tinyjs: Build JavaScript Desktop Apps in 10MB](https://tinyjs.app/)** (출처: *JavaScript Weekly #803*)
  ![tinyjs: Build JavaScript Desktop Apps in 10MB](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/l5ejacd7rpbkelmaxdto.jpg)
  + 개요: txiki.js 기반 JavaScript 백엔드에 OS 네이티브 웹뷰 창(macOS WebKit, Windows WebView2, Linux WebKitGTK)을 결합한 데스크톱 앱 런타임입니다. 공식 사이트 기준으로 배포 크기는 약 6MB입니다(Electron 150MB 이상, Tauri 약 10MB). 페이지와 백엔드는 Unix 소켓으로 통신해 열리는 포트가 없고, 백엔드에서는 파일, 소켓, 프로세스, FFI, sqlite, fetch를 쓸 수 있습니다.
  + 사용법:
```bash
    tinyjs new myapp
    cd myapp
    tinyjs dev     # 창이 열리고 핫 리로드
    tinyjs build   # macOS는 서명된 .app 번들 생성
```
```javascript
    // src/main.js — 백엔드 전체
    export const api = {
      hello: async ({ name }) => `hi ${name}`,
    };
    // 페이지에서: await tiny.api.call('hello', { name });
```
  + 실전 팁: `tinyjs new myapp --template react-ts`처럼 vue-ts, svelte-ts, solid-ts, vanilla-ts 템플릿으로 Vite 기반 프로젝트를 시작할 수 있습니다. 대안으로 뉴스레터는 Electrobun(멀티 윈도우와 GPU 기능은 풍부하지만 런타임이 더 큼), Perry(TypeScript를 네이티브로 컴파일해 AppKit/Win32/GTK4 위젯 사용), Neutralinojs(더 작지만 범용 JS 백엔드가 없음)를 함께 소개합니다. 사이트에 따르면 macOS는 안정 단계이고 Windows와 Linux는 베타이며, 렌더링 엔진이 OS마다 달라 세 플랫폼 모두에서 테스트해야 합니다.
- **[@shadcn/lint: An Agent-First Linter for Tailwind](https://github.com/shadcn-ui/lint)** (출처: *JavaScript Weekly #803*)
  + 개요: Tailwind 프로젝트에서 "raw color 금지", "외부에서 `<Button>` 재스타일링 금지" 같은 규칙을 강제하는 ESLint/Oxlint 플러그인입니다. 위반 시 에러 메시지로 에이전트가 정의된 variant와 토큰을 쓰도록 유도합니다.
  + 실전 팁: 에이전트가 코드를 대량 생성하는 팀에서는 디자인 시스템 규칙을 프롬프트 대신 린트 규칙으로 고정하는 방식이 재현성 면에서 유리합니다.

[Alpha 1](https://github.com/reduxjs/react-redux/releases/tag/v9.4.0-alpha.1)에서 핵심 버그 수정과 벤치마크 정정이 이루어졌습니다.

## ✍️ 마치며
이번 주 소식에서 가장 눈에 띈 흐름은 "AI가 코드를 만드는 속도를 사람과 인프라가 어떻게 따라가는가"였습니다. Linear의 CI 재설계나 shadcn의 에이전트 전용 린터처럼, 품질 기준을 사람의 리뷰가 아니라 도구의 규칙으로 옮기려는 시도가 이어지고 있습니다. React-Redux의 시그널 실험은 규모가 커진 앱에서 상태 관리 비용이 어디서 발생하는지를 다시 보게 하고, Copilot 앱 사례는 높이를 예측할 수 없는 콘텐츠를 다룰 때 "언제 측정하고 어떻게 보정하는가"가 설계의 핵심임을 보여 줍니다. 한편 Next.js의 치명적인 취약점과 공급망 공격 수사 소식은, 기능 개발 속도만큼 의존성 관리와 배포 권한의 점검도 꾸준히 이어가야 한다는 점을 상기시킵니다.
