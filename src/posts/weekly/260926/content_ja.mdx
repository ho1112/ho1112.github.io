## 🔥 今週の主要テーマ
AIエージェントがコードを大量に生み出す時代に合わせて、パフォーマンスと品質をどう守るかをあらためて問い直す一週間でした。React-Reduxはシグナルベースのselectorでdispatchのコストを減らそうとしており、GitHub Copilotアプリは100万行のPRをReactの外でレンダリングし、LinearはCIのコストを設計し直しました。デスクトップアプリはtinyjsのように6MB台まで小さくなり、ブラウザではSafari 27とChromeがネイティブ機能を急速に増やしています。一方、Next.jsの致命的なRCEの修正とサプライチェーン攻撃のニュースは、セキュリティ点検の必要性をあらためて思い起こさせます。

## 1. 🔍 深掘り
- **[Rendering Huge Pull Requests in the GitHub Copilot App](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)** (出典: *React Status #492*)
  ![Rendering Huge Pull Requests in the GitHub Copilot App](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/wurtgptbln8tma7ldkus.jpg)
   - 背景: リファクタリングやマイグレーションは1つのPRにまとめなければならないことがあり、レビューのやり取りが増えるほどPRはさらに大きくなります。GitHubチームは、2,200ファイル、100万行を超える変更、400件を超えるインラインコメントがあるPRを基準に、Copilotアプリのdiff画面を作り直しました。
   - 主な機能: コード行は高さを事前に計算できるため、仮想化、typed arrayベースのオフセット計算、Reactコンポーネントを使わないimperativeな行レンダラーで処理します。一方、コメントはレンダリングしてみないと高さが分からないため、高さの計算を2つの領域に分けました。コードのジオメトリは正確な値で固定し、動的ブロック(レビュースレッド、返信入力欄など)は推定してから測定で補正します。測定はブロックごとにResizeObserverを置く代わりに、スクロールが止まった後、ビューポートの約2400px内側にあるブロックだけを一度にまとめて読み取る方式で、補正時にはユーザーが見ていた行やブロックを基準にスクロール位置を維持します。
   - コード例:
```text
     total height = deterministic code height          (exact, known up front)
                  + Σ dynamic block effective heights   (estimated, then measured)
                  + scroll padding
```
   - 実務での活用: 高さを予測できないコンテンツが混在する仮想リスト(チャット、コメントスレッド、フィード)で、「確定した高さ」と「測定した高さ」を別々のインデックスに分離する設計が参考になります。記事では、自身の状態を点検する構造化されたプローブを画面に常時置き、合成した大規模PRフィクスチャでE2Eの予算を検証し、変更・測定・改善のループを自動化した過程も紹介されています。
   - 注意事項: オブザーバーが自分で観察している要素のレイアウト高さを直接更新すると、フィードバックループが発生します。また、「ユーザーがスクロール中か」を判別する際に、画面自身が引き起こしたスクロール(サイドバーのトグル後の再配置など)と区別しないと、補正がスキップされて見ていた位置がずれてしまいます。
- **[The Root Scroller and How Not to Lose It](https://polypane.app/blog/the-root-scroller-and-how-not-to-lose-it/)** (出典: *Frontend Focus #759*)
   - 背景: root scrollerはビューポートのスクロールコンテナで、スクロール復元やモバイルのアドレスバーの折りたたみといったブラウザ機能を担っています。
   - 主な機能: よく使われるCSSパターンがスクロールを別の要素に移してしまうと、これらの機能が失われることをデモで示しています。
   - 実務での活用: レイアウトを `height: 100%` と内部スクロールコンテナで構成しているアプリなら、ビューポートのスクロールを失っていないか点検してみる価値があります。
   - 注意事項: スクロールコンテナを変えるCSSを導入する際は、スクロール復元とモバイルのアドレスバーの挙動が一緒に壊れていないかを確認する必要があります。

## 2. 🛠️ ツール & ライブラリ
- **[tinyjs: Build JavaScript Desktop Apps in 10MB](https://tinyjs.app/)** (出典: *JavaScript Weekly #803*)
  ![tinyjs: Build JavaScript Desktop Apps in 10MB](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/l5ejacd7rpbkelmaxdto.jpg)
  + 概要: txiki.jsベースのJavaScriptバックエンドに、OSネイティブのWebViewウィンドウ(macOSはWebKit、WindowsはWebView2、LinuxはWebKitGTK)を組み合わせたデスクトップアプリランタイムです。公式サイトによると、配布サイズは約6MBです(Electronは150MB以上、Tauriは約10MB)。ページとバックエンドはUnixソケットで通信するため開いているポートがなく、バックエンドではファイル、ソケット、プロセス、FFI、sqlite、fetchを使えます。
  + 使い方:
```bash
    tinyjs new myapp
    cd myapp
    tinyjs dev     # ウィンドウが開いてホットリロード
    tinyjs build   # macOSでは署名済みの.appバンドルを生成
```
```javascript
    // src/main.js — バックエンド全体
    export const api = {
      hello: async ({ name }) => `hi ${name}`,
    };
    // ページ側から: await tiny.api.call('hello', { name });
```
  + 実践チップ: `tinyjs new myapp --template react-ts` のように、vue-ts、svelte-ts、solid-ts、vanilla-tsテンプレートでViteベースのプロジェクトを始められます。代替手段として、ニュースレターではElectrobun(マルチウィンドウとGPU機能は豊富ですがランタイムがより大きい)、Perry(TypeScriptをネイティブにコンパイルしてAppKit/Win32/GTK4ウィジェットを使用)、Neutralinojs(より小さいが汎用JSバックエンドがない)もあわせて紹介しています。サイトによるとmacOSは安定版でWindowsとLinuxはベータ段階であり、レンダリングエンジンがOSごとに異なるため、3つのプラットフォームすべてでテストする必要があります。
- **[@shadcn/lint: An Agent-First Linter for Tailwind](https://github.com/shadcn-ui/lint)** (出典: *JavaScript Weekly #803*)
  + 概要: Tailwindプロジェクトで「raw colorの禁止」、「外部から `<Button>` を再スタイリングすることの禁止」といったルールを強制するESLint/Oxlintプラグインです。違反時のエラーメッセージで、エージェントが定義済みのvariantとトークンを使うよう誘導します。
  + 実践チップ: エージェントがコードを大量生成するチームでは、デザインシステムのルールをプロンプトではなくlintルールとして固定する方式が、再現性の面で有利です。

## ✍️ おわりに
今週のニュースで最も目を引いた流れは、「AIがコードを生み出す速度に、人とインフラがどう追いつくのか」でした。LinearのCI再設計やshadcnのエージェント専用linterのように、品質基準を人のレビューではなくツールのルールへ移そうとする試みが続いています。React-Reduxのシグナル実験は、規模が大きくなったアプリで状態管理のコストがどこで発生するのかをあらためて見直させ、Copilotアプリの事例は、高さを予測できないコンテンツを扱うときに「いつ測定し、どう補正するか」が設計の核心であることを示しています。一方、Next.jsの致命的な脆弱性とサプライチェーン攻撃の捜査のニュースは、機能開発の速度と同じくらい、依存関係の管理とデプロイ権限の点検も地道に続けなければならないことを思い出させます。
