## 이번 주 핵심 테마
- 이번 주는 "얼마나 가볍고 빠른가"를 다시 따져보는 소식이 중심이었습니다. TanStack Redact는 React 런타임을 통째로 줄이는 시도를 내놓았고, 디자인 시스템 10종을 같은 조건에서 측정한 결과는 인기 라이브러리도 인터랙션 지연이 크다는 점을 보여줬습니다. 플랫폼 쪽에서는 Chrome의 HTML-in-Canvas가 DOM과 캔버스의 경계를 허물었고, TypeScript 7.1 베타는 Vue·Svelte 같은 프레임워크 도구가 새 컴파일러로 넘어갈 길을 열었습니다. 한편 DeadTag는 방치된 서드파티 태그가 공급망 공격 경로가 될 수 있음을 상기시켰습니다.

## 1. 🔍 심층 분석
- **[HTML-in-Canvas: Interactive DOM Inside 2D, WebGL and WebGPU Canvases](https://developer.chrome.com/blog/html-in-canvas)** (출처: *Frontend Focus #764*)
  ![HTML-in-Canvas: Interactive DOM Inside 2D, WebGL and WebGPU Canvases](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/v1793190176/dlisimtjkn0bavqwusxs.png)
  - 배경: 3D 장면 안에 HTML을 넣으려면 iframe 결과를 이미지로 바꾸는 복잡한 우회가 필요했고, 그 과정에서 텍스트 선택이나 접근성이 사라졌습니다.
  - 핵심 기능: 라이브 DOM 서브트리를 2D, WebGL, WebGPU 캔버스에 직접 그리면서도 텍스트 선택, 폼 컨트롤, Find-in-Page, 스크린리더가 그대로 동작합니다. 브라우저 번역·자동완성과 DevTools 검사도 지원됩니다. Three.js, Babylon.js, PixiJS가 이미 실험적으로 지원합니다.
  - 코드 예제:
    ```js
    const material = new THREE.MeshBasicMaterial();
    material.map = new THREE.HTMLTexture(uiElement);
    ```
  - 실무 적용: WebXR나 게임의 3D 장면 안에 읽을 수 있는 UI(터미널, 책 등)를 배치하거나, 캔버스 중심의 데이터 밀집 UI에 접근성을 유지한 채 HTML을 얹을 때 유용합니다.
  - 주의사항: 현재 Chrome 전용입니다. API를 쓸 수 없는 환경에서는 플로팅 HTML 오버레이나 html2canvas, dom-to-image 같은 대체 수단을 폴백으로 준비해야 합니다.
- **[DeadTag: Forgotten Third-Party Script Tags Became a Delivery Network for Spyware](https://blog.report-uri.com/deadtag-how-forgotten-website-tags-became-a-delivery-network-for-iphone-spyware/)** (출처: *Frontend Focus #764*)
  ![DeadTag: Forgotten Third-Party Script Tags Became a Delivery Network for Spyware](https://storage.ghost.io/c/2d/aa/2daa4f7f-a71b-47d2-a54c-06b8c60222ef/content/images/size/w2000/2026/10/DeadTag.png)
  - 배경: 한때 분석, 광고, 위젯 스크립트가 쓰던 도메인이 만료되면서, 이를 가리키는 옛 태그가 사이트에 그대로 남아 있는 경우가 많습니다.
  - 핵심 기능: 공격자가 만료 도메인을 사들이면, 해당 태그를 아직 가진 사이트는 공격자 코드를 조용히 불러오게 됩니다. 제목에서 보듯 이 경로가 iPhone 스파이웨어 유포망으로 쓰였습니다.
  - 실무 적용: 사이트에 박혀 있는 서드파티 태그와 그 도메인의 현재 상태를 정기적으로 점검해, 더는 쓰지 않는 태그를 제거하는 것이 가장 직접적인 대응입니다.

## 2. 🛠️ 툴 & 라이브러리
- **[TanStack Redact: A Smaller React for the Browser](https://tanstack.com/blog/introducing-tanstack-redact)** (출처: *React Status #495*)
  + 개요: 브라우저에서 React/React DOM을 대체하는 더 작은 구현체입니다. 빌드 설정에 추가하면 기존 import, 컴포넌트, 훅이 그대로 Redact를 쓰며, TanStack Start, Vite, Vinext, Next.js를 지원합니다. Vinext와 Next.js에서는 서버의 React는 유지하고 브라우저의 hydration과 렌더링만 Redact가 맡습니다.
  + 크기 절감(gzip, 동일한 작은 앱 기준): Vite 68.3KB에서 20.1KB(70.5% 감소), TanStack Start 43.0%, Vinext 28.5%, Next.js 20.4% 감소입니다.
  + 실전 팁: 동기 렌더링이라 시간 분할(time slicing)이 없어서 무거운 렌더가 입력을 지연시킬 수 있습니다. 앱에서 가장 바쁜 화면에 먼저 적용해 보고 호환성 가이드를 확인하세요. r/reactjs에서는 한 테스터가 프로덕션 사이트 두 곳에서 재렌더링 CPU 비용이 약 2배라고 보고했습니다.
- **[Structs: TC39's Shared Structs Proposal, But Usable Today](https://structs.arv.tools/)** (출처: *JavaScript Weekly #808*)
  + 개요: 전 TC39 대의원이 Stage 2 structs 제안을 구현했습니다. 워커 간 공유 메모리로 스레드가 복사본을 직렬화해 주고받지 않고 같은 객체를 다룹니다. 브라우저에서 바로 써볼 수 있는 playground도 있습니다.

  + 핵심 인사이트: 단일 최악값으로 예산을 잡으면 이상치 하나가 진짜 성능 저하를 가립니다. 최근 데이터의 P90 또는 P95 같은 "대표적 최악"에서 출발하라고 Harry Roberts가 자신의 기존 조언을 수정합니다. 스프레드시트 템플릿이 포함되어 바로 적용해 볼 수 있습니다.

  + 핵심 인사이트: 안 쓰는 코드가 생각보다 큰 비용을 낸다는 점과, Sentry가 [Knip](https://knip.dev/)으로 2만 8천 줄을 제거한 과정을 다룹니다. 여섯 개 컨퍼런스에서 발표된 내용이 슬라이드와 전체 스크립트로 정리되어 있습니다.

## 마치며
이번 주 소식을 훑어보면 번들 크기와 런타임 비용을 다시 묻는 흐름이 뚜렷했습니다. Redact는 앱 코드를 건드리지 않고 클라이언트 번들을 크게 줄일 수 있음을 보여주었지만, 동기 렌더링이라는 대가가 있으므로 가장 무거운 화면에서의 입력 지연을 직접 측정해 판단해야 한다고 생각합니다. 디자인 시스템 측정 결과도 같은 교훈을 줍니다. 번들 크기만 감시하면 클릭 이후의 지연은 보이지 않기 때문입니다. 반대로 DeadTag는 코드를 줄이는 일만큼 오래된 의존성을 정리하는 일도 중요하다는 점을 상기시켰습니다. 새 기능을 도입하기 전에 지금 쓰고 있는 것의 상태를 점검하는 습관이 결국 가장 저렴한 최적화이자 방어일 것입니다.
