## 今週の主要テーマ
- 今週は「どれだけ軽く、速いか」をあらためて問い直す話題が中心でした。TanStack Redactは、Reactランタイムそのものを小さくする試みを打ち出しました。デザインシステム10種を同じ条件で計測した結果は、人気のライブラリでもインタラクションの遅延が大きいことを示しました。プラットフォーム側では、ChromeのHTML-in-CanvasがDOMとキャンバスの境界を取り払い、TypeScript 7.1 Betaは、VueやSvelteのようなフレームワーク系ツールが新しいコンパイラへ移行するための道を開きました。一方でDeadTagは、放置されたサードパーティタグがサプライチェーン攻撃の経路になり得ることを改めて思い出させました。

## 1. 🔍 深掘り
- **[HTML-in-Canvas: Interactive DOM Inside 2D, WebGL and WebGPU Canvases](https://developer.chrome.com/blog/html-in-canvas)** (出典: *Frontend Focus #764*)
  ![HTML-in-Canvas: Interactive DOM Inside 2D, WebGL and WebGPU Canvases](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/v1793190176/dlisimtjkn0bavqwusxs.png)
  - 背景: 3Dシーンの中にHTMLを入れるには、iframeの結果を画像に変換するという複雑な回避策が必要で、その過程でテキスト選択やアクセシビリティが失われていました。
  - 主な機能: ライブなDOMサブツリーを2D、WebGL、WebGPUのキャンバスに直接描画しながらも、テキスト選択、フォームコントロール、ページ内検索、スクリーンリーダーがそのまま動作します。ブラウザの翻訳・オートフィルやDevToolsでの検査にも対応しています。Three.js、Babylon.js、PixiJSがすでに実験的にサポートしています。
  - コード例:
    ```js
    const material = new THREE.MeshBasicMaterial();
    material.map = new THREE.HTMLTexture(uiElement);
    ```
  - 実務での活用: WebXRやゲームの3Dシーン内に読めるUI(ターミナルや本など)を配置したり、キャンバス中心のデータ密度の高いUIに、アクセシビリティを保ったままHTMLを重ねたりする場合に便利です。
  - 注意事項: 現時点ではChrome専用です。APIが使えない環境に備えて、フローティングHTMLオーバーレイやhtml2canvas、dom-to-imageといった代替手段をフォールバックとして用意しておく必要があります。
- **[DeadTag: Forgotten Third-Party Script Tags Became a Delivery Network for Spyware](https://blog.report-uri.com/deadtag-how-forgotten-website-tags-became-a-delivery-network-for-iphone-spyware/)** (出典: *Frontend Focus #764*)
  ![DeadTag: Forgotten Third-Party Script Tags Became a Delivery Network for Spyware](https://storage.ghost.io/c/2d/aa/2daa4f7f-a71b-47d2-a54c-06b8c60222ef/content/images/size/w2000/2026/10/DeadTag.png)
  - 背景: かつて分析、広告、ウィジェットのスクリプトが使っていたドメインが失効し、それを指す古いタグがサイトにそのまま残っているケースが多くあります。
  - 主な機能: 攻撃者が失効したドメインを購入すると、そのタグをまだ持っているサイトは、攻撃者のコードを知らないうちに読み込んでしまいます。タイトルにあるとおり、この経路がiPhoneスパイウェアの配布網として使われました。
  - 実務での活用: サイトに埋め込まれているサードパーティタグとそのドメインの現在の状態を定期的に点検し、使っていないタグを削除することが、最も直接的な対策です。

## 2. 🛠️ ツール & ライブラリ
- **[TanStack Redact: A Smaller React for the Browser](https://tanstack.com/blog/introducing-tanstack-redact)** (出典: *React Status #495*)
  + 概要: ブラウザ上でReact/React DOMを置き換える、より小さな実装です。ビルド設定に追加すれば、既存のimport、コンポーネント、フックがそのままRedactを使うようになり、TanStack Start、Vite、Vinext、Next.jsをサポートしています。VinextとNext.jsでは、サーバー側のReactは維持され、ブラウザでのhydrationとレンダリングだけをRedactが担います。
  + サイズ削減(gzip、同一の小さなアプリ基準): Viteは68.3KBから20.1KB(70.5%削減)、TanStack Startは43.0%、Vinextは28.5%、Next.jsは20.4%の削減です。
  + 実践的なヒント: 同期レンダリングのためタイムスライシング(time slicing)がなく、重いレンダリングが入力を遅延させる可能性があります。アプリで最も負荷の高い画面から先に適用してみて、互換性ガイドを確認してください。r/reactjsでは、あるテスターが本番サイト2か所で再レンダリングのCPUコストが約2倍になったと報告しています。
- **[Structs: TC39's Shared Structs Proposal, But Usable Today](https://structs.arv.tools/)** (出典: *JavaScript Weekly #808*)
  + 概要: 元TC39デリゲートが、Stage 2のstructs提案を実装しました。ワーカー間の共有メモリにより、スレッドがコピーをシリアライズしてやり取りすることなく、同じオブジェクトを扱えます。ブラウザですぐ試せるplaygroundも用意されています。

## 3. 📝 おすすめ記事 & チップ
- **[React.lazy, Suspense and the Hidden 300ms Startup Delay](https://tabwidgets.com/blog/react-lazy-suspense-delay)** (出典: *React Status #495*)
  ![React.lazy, Suspense and the Hidden 300ms Startup Delay](https://assets.tabwidgets.com/cdn-cgi/image/width=1600,format=auto,quality=80/images/posts/2026/10/react-lazy-suspense-delay/startup-timeline-windows.png)
  + 主要なインサイト: コードがすでにロード済みのlazyコンポーネントでも初回レンダリングでsuspendすることがあり、Reactがsuspendされたコンテンツの表示を300msに一度に制限(throttle)する場合があります。あるチームがこの遅延を追跡した過程と解決策をまとめています。体感速度の問題を、ネットワークではなくレンダリングのスケジューリング側から探るきっかけになる記事で、とても有益です。
- **[Performance Budgets Need a Representative Worst](https://csswizardry.com/2026/10/web-perf-wednesday-014-performance-budgets-need-a-representative-worst/)** (出典: *Frontend Focus #764*)
  + 主要なインサイト: 単一の最悪値で予算を決めると、外れ値ひとつが本当の性能劣化を覆い隠してしまいます。直近データのP90やP95のような「代表的な最悪値」から始めるよう、Harry Robertsが自身のこれまでの助言を修正しています。スプレッドシートのテンプレートが付いているので、すぐに試せます。
- **[Dead Code Shouldn't Exist: How Sentry Cut 28,000 Lines](https://tkdodo.eu/blog/dead-code-shouldnt-exist)** (出典: *JavaScript Weekly #808*)
  + 主要なインサイト: 使われていないコードが思った以上に大きなコストを生むことと、Sentryが[Knip](https://knip.dev/)で2万8千行を削除した過程を扱っています。6つのカンファレンスで発表された内容が、スライドと全文スクリプトにまとめられています。

## おわりに
今週のニュースを振り返ると、バンドルサイズとランタイムコストをあらためて問う流れがはっきりしていました。Redactは、アプリのコードに手を入れずにクライアントバンドルを大きく減らせることを示しましたが、同期レンダリングという代償があるため、最も重い画面での入力遅延を自分で計測して判断すべきだと思います。デザインシステムの計測結果も同じ教訓を与えてくれます。バンドルサイズだけを監視していると、クリック後の遅延は見えないからです。逆にDeadTagは、コードを減らすことと同じくらい、古い依存関係を整理することが重要だと改めて思い出させました。新しい機能を導入する前に、今使っているものの状態を点検する習慣こそが、結局のところ最も安上がりな最適化であり、防御なのでしょう。
