## 🔥 이번 주 핵심 테마
- AI 에이전트가 코드를 쓰는 시대에 프레임워크 선택 기준을 다시 묻는 벤치마크가 화제였습니다. 비용 차이는 불분명했지만 브라우저로 전달되는 JavaScript 양에서는 뚜렷한 격차가 드러났습니다. 한편 npm 패키지 쿨다운, 서드파티 스크립트 하이재킹, GitHub Actions의 pull_request_target 차단 등 공급망 보안 이슈가 이어졌고, Discord의 Rust 전환과 Parcel 3의 Rust 재작성처럼 네이티브 언어로 무게중심이 옮겨가는 흐름도 눈에 띄었습니다. Safari는 사이트 대신 다크 모드를 입혀 주는 기능을 베타로 선보였습니다.

## 1. 🔍 심층 분석
- **[The AI Cost of JavaScript Frameworks](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)** (출처: *JavaScript Weekly #809*)
  ![The AI Cost of JavaScript Frameworks](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/dhcgdjewfv50joacutkm.jpg)
   - 배경: "특정 프레임워크가 에이전트에게 더 낫다"는 주장을 검증하기 위해 Nolan Lawson이 Claude에게 같은 앱을 12개 JS 스택에서 각각 5번씩 만들게 했습니다.
   - 핵심 기능: 실행마다 비용 편차가 컸고, Gautam Parab은 관측된 비용 범위가 대부분의 프레임워크 쌍에서 겹치거나 맞닿는다고 [분석](https://gautamparab.com/writing/sixty-of-sixty-six-ranges-overlap/)했습니다. 반면 브라우저로 전송된 JavaScript 중앙값에서는 분명한 차이가 났습니다. Astro 0KB, Hono+htmx 18K, SvelteKit 36K, React Router·TanStack Start·Next.js는 115~142K였습니다.
   - 실무 적용: 코드를 직접 쓰지 않는 "hands-free" 개발이라면 왜 직접 코드를 쓰던 시절에 고른 스택을 그대로 유지하는지 되물어볼 수 있습니다. [벤치마크 저장소](https://github.com/nolanlawson/agent-framework-benchmark)가 공개되어 있어 직접 돌려볼 수 있습니다.
   - 주의사항: 비용은 실행 간 편차가 커서 한두 번의 측정값으로 프레임워크 우열을 가르기는 어렵습니다.
- **[Safari Introduces Adaptive Dark Mode](https://webkit.org/blog/18541/introducing-adaptive-dark-mode/)** (출처: *Frontend Focus #765*)
  ![Safari Introduces Adaptive Dark Mode](https://webkit.org/wp-content/uploads/Demo-of-Adaptive-Dark-Mode_light.png)
   - 배경: 페이지 로드의 약 40%가 다크 모드를 쓰는 사용자에게서 발생하지만, 다크 모드를 직접 지원하는 페이지 로드는 약 10%에 그칩니다.
   - 핵심 기능: Safari 27.3 베타에 추가된 기능으로, 라이트 사이트를 자동으로 다크 사이트처럼 보이게 변환합니다.
   - 주의사항: 사용자가 켜야 동작하는 opt-in 방식이며 아직 베타 단계입니다.

## 2. 🛠️ 툴 & 라이브러리
- **[Parcel 3 Alpha: A Rust Rewrite with React Compiler, Tailwind and RSC](https://v3.parceljs.org/blog/v3-alpha/)** (출처: *React Status #496*)
  + 개요: Parcel의 코어가 Node 의존성 없는 Rust 바이너리로 바뀌었고, 팀은 콜드 빌드가 v2보다 최대 100배 빨라졌다고 밝혔습니다. React Compiler(opt-in), Tailwind, MDX가 내장되고 RSC 지원은 베타입니다.
  + 실전 팁: React Compiler는 opt-in이고 RSC는 베타이므로, 도입 시 어떤 기능이 아직 실험 단계인지 구분해서 확인해야 합니다.

  + 개요: Anthony Fu가 만든 [i18n-ally](https://github.com/lokalise/i18n-ally)의 후속 도구로, 로케일 파일과 번역 호출을 스캔해 누락·미사용·깨진 키를 보고합니다.
  + 실전 팁: tsc --noEmit이 타입 오류를 알려주듯 번역 키 문제를 알려주는 방식이라, 타입 체크와 비슷한 감각으로 점검 단계에 넣어 쓸 수 있습니다.

에이전트가 코드를 쓰는 환경에서는 프레임워크를 고르는 기준도 달라져야 한다는 점이 이번 주 가장 인상적이었습니다. 비용 차이는 불분명했지만 사용자에게 전달되는 JavaScript 양은 숫자로 분명하게 갈렸고, 결국 결과물의 무게가 선택 기준이 될 수 있다고 느꼈습니다. 또한 패키지 쿨다운, SRI, pull_request_target 기본 차단처럼 공급망 보안 대응이 설정과 정책의 영역으로 내려오고 있어, 개별 도구보다 팀의 기본 설정을 점검하는 일이 중요해졌습니다. Discord와 Parcel이 Rust로 향하는 흐름까지 겹쳐 보면, 프런트엔드 개발자가 다루는 경계가 계속 넓어지고 있음을 실감합니다.
