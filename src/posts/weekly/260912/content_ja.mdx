## 1. 🔍 深掘り
- **[How Turbopack Chunks Your JavaScript](https://nextjs.org/blog/turbopack-chunking)** (出典: *JavaScript Weekly #801*)
  ![How Turbopack Chunks Your JavaScript](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/wq9zwktpt9rxrly3oo74.jpg)
  - 背景: Next.jsアプリは数十個のJavaScript「チャンク」に分割されてロードされます。Turbopackチームはnextjs.org自体を対象に「never merge / デフォルト / グループ内全体結合」という3つの設定で実測データを収集し、リクエスト数と転送コード量の間のトレードオフを公開しました。
  - 主要機能: Turbopackはチャンクグループ内でキャッシュの効果を見積もって結合の可否を判断し、単一ページセッションと複数ページセッションを別々に計算します。nextjs.orgの実測では、デフォルト設定は結合なしと比べてリクエスト数を半分以上減らしつつコード量もわずかに減りましたが、最大結合はリクエスト数をさらに減らす代わりにコード量が10%増加しました。結合の判断はビルド時に行われるため、訪問者のブラウザキャッシュの状態を反映できないという限界も指摘されています。
  - コード例:
```ts
    // next.config.ts
    const nextConfig = {
      experimental: {
        turbopackChunking: {
          minChunkSize: 50000,
          maxChunkCountPerGroup: 40,
          maxMergeChunkSize: 200000,
          generateComponentChunks: false,
        },
      },
    }
```
  - 実務での活用: ページ遷移が多いサイトであればデフォルト設定(積極的な結合)が有利で、初回ロード1回が重要なランディングページ的なサービスであれば結合を減らす方が有利な場合があります。`generateComponentChunks`を有効にすると、ルート単位ではなくコンポーネント単位でキャッシュを意識したチャンクを作成できます。
  - 注意事項: これらのオプションはまだ実験的(experimental)な機能であるためプロダクションでの利用は推奨されておらず、ビルド時点での判断であるという根本的な限界は残っています。

## 3. 📝 おすすめ記事 & チップ
- **[Half Past Fetch: What await fetch() Waits For](https://blog.gaborkoos.com/posts/2026-09-08-Half-Past-Fetch/)** (出典: *JavaScript Weekly #801*)
  - 背景: `await fetch(url)`はレスポンス全体を待つと誤解されがちですが、実際にはヘッダーまでを待ってresolveされます。
  - 主要なインサイト: 仕様上、HTTP-network fetchアルゴリズムはサーバーが送る1xxステータス行をスキップし、最終的なステータス行が到着した瞬間に新しい`ReadableStream`を付けてレスポンスを返します。つまり`response.body`はまだ埋まり続けているストリームであり、この隙間のために`clone()`がまだ完成していない内容をコピーする仕組みや、`abort()`がヘッダー以降の段階で異なる挙動をする理由、そして想定していたタイムアウトが実際にはリクエスト全体をカバーできない理由が説明されています。
  - コード例:
```js
    const t0 = performance.now()
    const response = await fetch(url)
    console.log('headers', performance.now() - t0, response.status)
    await response.arrayBuffer() // 本文までにかかった実際の時間はここで明らかになる
```
  - この記事が役立つ理由: ヘッダー到着と本文完了の間のギャップを知らないと、`clone()`や`abort()`、タイムアウト関連のバグに遭遇したときに見当違いの場所で原因を探すことになります。実務でよく見られるfetch関連の誤動作の根本原因を、仕様レベルで明らかにしてくれます。
- **[New Things You Should Know About HTML in 2026](https://blog.master.dev/new-things-you-should-know-about-html-here-in-mid-2026/)** (出典: *Frontend Focus #757*)
  - 背景: かつての汎用的な`<permission>`エレメントの実験は廃止され、代わりに`<geolocation>`のように用途別に具体的な権限エレメントを導入する方向へとHTMLが進化しています。
  - 主要なインサイト: `<usermedia>`はカメラ・マイクへのアクセスフロー全体を管理し、ユーザーの意図を捉え、ブラウザのプロンプトを表示し、`MediaStream`オブジェクトをアプリケーションに渡します。画面上に実際に見えるボタンであるため、ユーザーが一度権限を拒否しても、設定メニューを探し回ることなく再度ボタンを押して気持ちを変えられる「復旧経路」が自然に生まれます。対応していないブラウザでは意味を持たない`<span>`のように無視され、プログレッシブエンハンスメントとして動作します。
  - コード例:
```html
    <usermedia id="media-ctrl">
      <button>Enable camera and microphone</button>
    </usermedia>
```
  - この記事が役立つ理由: `getUserMedia()`の呼び出しや手動のプロンプト処理といったボイラープレートを取り除けるフローをあらかじめ把握しておくと、今後このような宣言的な権限エレメントが標準化された際に、移行の負担を減らすことができます。
- **[The Browser's Main Thread is Expensive](https://kciter.so/posts/the-expensive-main-thread/en/)** (出典: *Frontend Focus #757*、*JavaScript Weekly #801* 同時掲載)
  ![The Browser's Main Thread is Expensive](https://kciter.so/images/2026-07-12-the-expensive-main-thread/thumbnail.png)
  - 背景: メインスレッドに作業が集中するとインタラクションが途切れる問題を扱っており、2つのニュースレターで同時に紹介されるほど反響が大きかった記事です。
  - 主要なインサイト: 著者はsplitting(作業の分割)・batching(作業のまとめ)・prioritizing(順序付け)・deferring(先送り)という4つの手法で整理しています。例えば、人気のライブ配信チャットでは1秒間に数百件ものメッセージが一気に押し寄せますが、これをどう分割して処理するかが最初の基準となり、タブを切り替えて戻ってきた際に画面外の投稿まで一括でスタイル・レイアウトを再計算してしまうフィードUIの事例で、deferringの必要性を示しています。
  - コード例: *(原文は概念・事例の説明が中心で、著者が提示したコードスニペットはありません。同じ文脈でよく使われる標準APIを参考として付け加えます。)*
```js
    // 例: 長い処理をアイドル時間に分けて処理する一般的なパターン
    function processInChunks(items, worker) {
      requestIdleCallback(() => {
        // 残り時間がある場合のみ次のバッチを処理
      })
    }
```
  - この記事が役立つ理由: 「何をどれだけ分割するか」と「いつ処理するか」を切り分けてアプローチするフレームを提示し、漠然とした「最適化が必要だ」という感覚を具体的なチェックリストへと変えてくれます。

## ✍️ おわりに
今週のニュースを見渡すと、実験的だったものが一つ、また一つと居場所を見つけていく流れが目につきます。ReactのView TransitionsとFragment Refsは、去年までは「実験的」というラベルが付いていましたが、今やプロダクションで使ってよいAPIになりました。HTMLの権限エレメントも、`<permission>`という汎用的な実験が廃止された跡地に、`<geolocation>`や`<usermedia>`のようなより具体的な解決策が根を下ろしつつあります。反対に、Shopifyが6年間続けたReact Nativeの歩みを終え、ネイティブへ回帰した事例は、特定の技術スタックへの賭けが組織の成長段階や優先順位によっていつでも見直され得ることを改めて示しています。Turbopackのチャンク結合ベンチマークやVitestのパフォーマンス重視のリリースに共通して感じられるのは、ツールがもはや「とにかく動くようにすること」を超えて、実測データを根拠にトレードオフを透明に公開する方向へと成熟しつつあるという点です。コードをどれだけ速く書けるかよりも、そのコードが実際のブラウザと実際のユーザーの前でどう動作するかを測ることが、ますます重要になってきているようです。
