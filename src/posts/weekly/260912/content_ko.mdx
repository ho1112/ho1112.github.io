## 1. 🔍 심층 분석
- **[How Turbopack Chunks Your JavaScript](https://nextjs.org/blog/turbopack-chunking)** (출처: *JavaScript Weekly #801*)
  ![How Turbopack Chunks Your JavaScript](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/wq9zwktpt9rxrly3oo74.jpg)
  - 배경: Next.js 앱은 수십 개의 JavaScript "청크"로 쪼개져 로드됩니다. Turbopack 팀은 nextjs.org 자체를 대상으로 "never merge / 기본값 / 그룹 내 전체 병합"이라는 세 가지 설정으로 실측 데이터를 수집해, 요청 수와 전송 코드량 사이의 트레이드오프를 공개했습니다.
  - 핵심 기능: Turbopack은 청크 그룹 내에서 캐싱 이득을 추정해 병합 여부를 결정하며, 단일 페이지 세션과 다중 페이지 세션을 따로 계산합니다. nextjs.org 실측에서는 기본 설정이 병합 없음 대비 요청 수를 절반 이상 줄이면서 코드량도 소폭 줄였지만, 최대 병합은 요청 수를 더 줄이는 대신 코드량이 10% 늘었습니다. 병합 결정은 빌드 타임에 이뤄지므로 방문자의 브라우저 캐시 상태를 반영하지 못한다는 한계도 짚었습니다.
  - 코드 예제:
```ts
    // next.config.ts
    const nextConfig = {
      experimental: {
        turbopackChunking: {
          minChunkSize: 50000,
          maxChunkCountPerGroup: 40,
          maxMergeChunkSize: 200000,
          generateComponentChunks: false,
        },
      },
    }
```
  - 실무 적용: 페이지 탐색이 잦은 사이트라면 기본값(적극적 병합)이 유리하고, 초기 로드 한 번이 중요한 랜딩 페이지 성격의 서비스라면 병합을 줄이는 쪽이 더 유리할 수 있습니다. `generateComponentChunks`를 켜면 라우트 단위가 아니라 컴포넌트 단위로 캐시 인지 청크를 만들 수 있습니다.
  - 주의사항: 이 옵션들은 아직 실험적(experimental) 기능이라 프로덕션에는 권장되지 않으며, 빌드 시점 결정이라는 근본적인 한계는 남아 있습니다.

## 3. 📝 추천 아티클 & 팁
- **[Half Past Fetch: What await fetch() Waits For](https://blog.gaborkoos.com/posts/2026-09-08-Half-Past-Fetch/)** (출처: *JavaScript Weekly #801*)
  - 배경: `await fetch(url)`이 응답 전체를 기다린다고 오해하기 쉽지만, 실제로는 헤더까지만 기다리고 resolve됩니다.
  - 핵심 인사이트: 스펙상 HTTP-network fetch 알고리즘은 서버가 보내는 1xx 상태줄을 건너뛰고 최종 상태 줄이 도착하는 순간 새 `ReadableStream`을 붙여 응답을 반환합니다. 즉 `response.body`는 여전히 채워지고 있는 스트림이며, 이 틈새 때문에 `clone()`이 아직 완성되지 않은 내용을 복사하는 방식이나 `abort()`가 헤더 이후 단계에서 다르게 동작하는 이유, 그리고 생각했던 타임아웃이 실제로는 요청 전체를 덮지 못하는 이유가 설명됩니다.
  - 코드 예시:
```js
    const t0 = performance.now()
    const response = await fetch(url)
    console.log('headers', performance.now() - t0, response.status)
    await response.arrayBuffer() // 본문까지 걸린 실제 시간은 여기서 드러남
```
  - 왜 이 글이 유익한지: 헤더 도착과 본문 완료 사이의 간극을 모르면 `clone()`, `abort()`, 타임아웃 관련 버그를 마주쳤을 때 원인을 엉뚱한 곳에서 찾게 됩니다. 실무에서 흔한 fetch 관련 오동작의 근본 원인을 스펙 레벨에서 짚어 줍니다.
- **[New Things You Should Know About HTML in 2026](https://blog.master.dev/new-things-you-should-know-about-html-here-in-mid-2026/)** (출처: *Frontend Focus #757*)
  - 배경: 예전의 범용 `<permission>` 엘리먼트 실험은 폐기되었고, 대신 `<geolocation>`처럼 용도별로 구체적인 권한 엘리먼트를 도입하는 방향으로 HTML이 진화하고 있습니다.
  - 핵심 인사이트: `<usermedia>`는 카메라·마이크 접근 플로우 전체를 관리하며 사용자의 의도를 포착하고, 브라우저 프롬프트를 띄우고, `MediaStream` 객체를 애플리케이션에 전달합니다. 화면에 실제로 보이는 버튼이기 때문에, 사용자가 한 번 권한을 거부해도 설정 메뉴를 뒤지지 않고 다시 버튼을 눌러 마음을 바꿀 수 있는 "복구 경로"가 자연스럽게 생깁니다. 지원하지 않는 브라우저에서는 의미 없는 `<span>`처럼 무시되어 프로그레시브 인핸스먼트로 동작합니다.
  - 코드 예시:
```html
    <usermedia id="media-ctrl">
      <button>Enable camera and microphone</button>
    </usermedia>
```
  - 왜 이 글이 유익한지: `getUserMedia()` 호출과 수동 프롬프트 처리 보일러플레이트를 걷어낼 수 있는 흐름을 미리 파악해두면, 이후 이런 선언적 권한 엘리먼트가 표준화될 때 마이그레이션 부담을 줄일 수 있습니다.
- **[The Browser's Main Thread is Expensive](https://kciter.so/posts/the-expensive-main-thread/en/)** (출처: *Frontend Focus #757*, *JavaScript Weekly #801* 동시 추천)
  ![The Browser's Main Thread is Expensive](https://kciter.so/images/2026-07-12-the-expensive-main-thread/thumbnail.png)
  - 배경: 메인 스레드에 작업이 몰리면 인터랙션이 끊기는 문제를 다루며, 두 뉴스레터에서 동시에 추천될 만큼 반응이 좋았던 글입니다.
  - 핵심 인사이트: 저자는 splitting(작업 쪼개기)·batching(작업 묶기)·prioritizing(순서 정하기)·deferring(미루기) 네 가지 기법으로 정리합니다. 예를 들어 인기 라이브 스트림 채팅방에서는 메시지가 초당 수백 개씩 한꺼번에 몰려오는데, 이를 어떻게 쪼개 처리하느냐가 첫 번째 기준이 되고, 탭을 전환했다가 돌아왔을 때 화면 밖에 있는 게시물까지 한꺼번에 스타일·레이아웃을 재계산하는 피드 UI 사례로 deferring의 필요성을 보여줍니다.
  - 코드 예시: *(원문은 개념·사례 설명 중심이라 저자가 제시한 코드 스니펫은 없습니다. 같은 맥락에서 흔히 쓰이는 표준 API를 참고용으로 덧붙입니다.)*
```js
    // 예: 긴 작업을 유휴 시간에 나눠 처리하는 일반적인 패턴
    function processInChunks(items, worker) {
      requestIdleCallback(() => {
        // 남은 시간이 있을 때만 다음 배치 처리
      })
    }
```
  - 왜 이 글이 유익한지: "무엇을 얼마나 쪼갤지"와 "언제 처리할지"를 구분해서 접근하는 프레임을 제시해, 막연히 "최적화가 필요하다"는 감각을 구체적인 체크리스트로 바꿔줍니다.

## ✍️ 마치며
이번 주 소식들을 훑어보면, 실험적이었던 것들이 하나둘 제자리를 찾아가는 흐름이 눈에 띕니다. React의 View Transitions와 Fragment Refs는 작년까지만 해도 "실험적" 딱지가 붙어 있었지만 이제는 프로덕션에서 써도 되는 API가 되었고, HTML의 권한 엘리먼트들도 `<permission>`이라는 범용 실험이 폐기된 자리에 `<geolocation>`, `<usermedia>` 같은 더 구체적인 해법으로 자리를 잡아가고 있습니다. 반대로 Shopify가 6년간의 React Native 여정을 접고 네이티브로 돌아간 사례는, 특정 기술 스택에 대한 베팅이 조직의 성장 단계나 우선순위에 따라 언제든 재검토될 수 있다는 점을 새삼 보여줍니다. Turbopack의 청크 병합 벤치마크나 Vitest의 성능 중심 릴리스에서 공통으로 느껴지는 것은, 이제 도구들이 "일단 되게 만드는 것"을 넘어 실측 데이터를 근거로 트레이드오프를 투명하게 공개하는 방향으로 성숙해지고 있다는 점입니다. 코드를 얼마나 빨리 쓰느냐보다, 그 코드가 실제 브라우저와 실제 사용자 앞에서 어떻게 동작하는지를 재는 일이 점점 더 중요해지는 듯합니다.
