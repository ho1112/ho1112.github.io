## 🔥 이번 주 핵심 테마

이번 주의 화두는 "오래 묵힌 오픈소스 프로젝트들의 대대적인 재설계"입니다. 4년 만에 나온 TanStack Table v9는 tree-shakable 플러그인 아키텍처로 다시 태어났고, Next.js 16.3은 팀을 재편하며 새 버전을 냈으며, htmx의 본질을 40줄로 직접 재구현해보는 글이 큰 주목을 받았습니다. 동시에 `keyv`·`cacheable` 패키지를 노린 npm 공급망 공격이 진행 중이라 "안전한 배포"가 실무 이슈로 떠올랐습니다. 한편 Frontend Focus는 State of CSS 2026 설문(개발자들이 가장 사랑하는 신기능 anchor positioning)을, Smashing은 접근성 특집을 전하며 한 주를 채웠습니다.

## 1. 🔍 심층 분석
- **[TanStack Table v9: A Faster, More Modular Foundation](https://tanstack.com/blog/announcing-tanstack-table-v9)** (출처: *React Status #486*)
  ![TanStack Table v9 announcement](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/tdvf8n2ypodcj3csupni.jpg)
  - 배경: v8이 나온 지 4년 만의 메이저 릴리스입니다. React Compiler가 정식화되면서 v8이 쓰던 상태 관리 패턴이 컴파일러 규칙과 충돌하기 시작했고, 이것이 내부 아키텍처 전면 재작성의 직접적인 계기가 되었습니다.
  - 핵심 기능: 모든 기능이 "opt-in" 방식으로 바뀌었습니다. 정렬·필터·페이지네이션 같은 기능을 `tableFeatures()`로 명시적으로 등록해야만 코드와 타입이 테이블에 포함됩니다. 상태 관리는 TanStack Store 기반으로 옮겨져 구독 단위의 세밀한 리렌더 제어가 가능해졌고, row·column·cell API가 공유 프로토타입에 올라가면서 대용량 테이블에서 메모리를 크게 절약합니다(일부 시나리오 최대 약 90%).
  - 코드 예제:
```js
    import {
      columnFilteringFeature,
      rowSortingFeature,
      rowPaginationFeature,
      tableFeatures,
      useTable,
    } from '@tanstack/react-table'

    // 필요한 기능만 등록 → 나머지 코드는 번들에서 제외(tree-shaking)
    const features = tableFeatures({
      columnFilteringFeature,
      rowSortingFeature,
      rowPaginationFeature,
    })

    function Table() {
      const table = useTable({ features, columns, data })
      // ... 헤드리스 렌더링은 v8과 동일한 모델
    }
```
  - 실무 적용: 페이지네이션만 필요한 테이블은 필터·그룹핑 코드를 아예 싣지 않습니다. 절반 정도의 기능만 쓰는 앱이라면 나머지 절반을 배송하지 않아도 되므로, 관리자 대시보드나 SaaS의 데이터 그리드처럼 화면마다 요구 기능이 다른 곳에서 유리합니다.
  - 주의사항: 잠재적 총 번들 크기는 v8의 약 14kB에서 v9의 약 25kB로 늘었습니다. 즉 `stockFeatures`로 전체 기능을 한 번에 쓰면 오히려 커지므로, 개별 기능을 하나씩 import 해야 tree-shaking 이점을 얻습니다. 기능 객체는 컴포넌트 바깥에 정적으로 정의하는 것이 권장됩니다.
- **[Let's Make the Worst htmx Ever](https://zserge.com/posts/worst-htmx-ever/)** (출처: *JavaScript Weekly #797*)
  - 배경: Serge Zaitsev가 "worst React", "worst Vue"에 이어 이번엔 htmx의 본질을 밑바닥부터 재구현합니다. 5천 줄짜리 단일 파일로 악명 높은 htmx가 실제로 하는 일이 무엇인지 직접 만들어보며 이해하자는 취지입니다.
  - 핵심 기능: 저자는 htmx의 정수를 "SSS"로 요약합니다. 즉 요소를 훑고(scan) → 요청을 보내고(send) → 응답을 갈아끼운다(swap). 이 세 가지만 있으면 htmx의 뼈대가 완성되고, 나머지 기능(부스팅, 인디케이터, 확인 대화상자 등)은 코어를 건드리지 않는 이벤트 기반 플러그인으로 붙입니다.
  - 코드 예제:
```js
    // x-get 속성을 훑어(scan) 클릭 시 fetch(send) 후 응답으로 교체(swap)
    document.querySelectorAll('[x-get]').forEach(el => {
      el.addEventListener('click', async (e) => {
        e.preventDefault()
        const res = await fetch(el.getAttribute('x-get'))
        el.outerHTML = await res.text() // 이것이 htmx의 핵심 10줄
      })
    })
```
  - 실무 적용: `beforeSend`·`afterSwap` 같은 커스텀 이벤트를 노출하면, 확인창·스피너·히스토리 갱신 같은 기능을 각각 열 몇 줄짜리 독립 플러그인으로 구현할 수 있습니다. 프레임워크의 "확장 지점"을 어떻게 설계해야 코어를 얇게 유지할 수 있는지에 대한 좋은 교보재입니다.
  - 주의사항: 저자 스스로 인정하듯 실패한 `fetch()`나 non-2XX 응답 처리, 프로미스 기반 취소, 뷰 트랜지션 대기 등은 빠져 있어 실제 htmx를 대체하지는 못합니다. 어디까지나 "동작 원리 학습용"으로 접근해야 합니다.

## ✍️ 마치며

이번 주 릴리스들을 관통하는 한 가지 흐름은 "필요한 만큼만 싣는다"는 철학이었습니다. TanStack Table v9가 기능을 opt-in으로 돌려세운 것, htmx의 본질을 40줄로 환원해 나머지를 플러그인으로 밀어낸 실험, 그리고 Base UI 같은 언스타일 라이브러리의 확산까지 프레임워크의 무게중심이 "다 갖춘 기본값"에서 "명시적으로 고르는 최소 코어"로 옮겨가고 있다는 인상을 받습니다. 코어를 얇게 유지하고 확장 지점을 잘 설계하는 일이, 결국 번들 크기와 유지보수성을 동시에 잡는 열쇠가 되는 듯합니다.

다른 한편으로 `keyv`·`cacheable` 공급망 공격은, 우리가 아무리 좋은 아키텍처를 짜도 그것을 배송하는 파이프라인이 뚫리면 소용없다는 사실을 다시 일깨웁니다. staged/trusted publishing 같은 배포 위생이 더 이상 선택이 아니라는 점, 그리고 Smashing이 짚은 것처럼 AI가 만들어 준 UI의 접근성을 우리가 직접 검증해야 한다는 점 결국 "생성"보다 "검증과 신뢰"가 이번 주의 진짜 주제였는지도 모르겠습니다.
