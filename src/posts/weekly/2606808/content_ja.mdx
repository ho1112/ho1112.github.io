## 🔥 今週の主要テーマ

今週のトピックは「長らく寝かされていたオープンソースプロジェクトの大々的な再設計」です。4年ぶりに登場したTanStack Table v9はtree-shakableなプラグインアーキテクチャとして生まれ変わり、Next.js 16.3はチームを再編して新バージョンをリリースし、htmxの本質を40行で自ら再実装してみる記事が大きな注目を集めました。同時に`keyv`・`cacheable`パッケージを狙ったnpmサプライチェーン攻撃が進行中で、「安全なデプロイ」が実務的な課題として浮上しました。一方、Frontend FocusはState of CSS 2026の調査(開発者が最も愛している新機能はanchor positioning)を、Smashingはアクセシビリティ特集を伝え、一週間を彩りました。

## 1. 🔍 深掘り
- **[TanStack Table v9: A Faster, More Modular Foundation](https://tanstack.com/blog/announcing-tanstack-table-v9)** (出典: *React Status #486*)
  ![TanStack Table v9 announcement](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/tdvf8n2ypodcj3csupni.jpg)
  - 背景: v8のリリースから4年ぶりのメジャーリリースです。React Compilerが正式化されるにつれ、v8が使っていた状態管理パターンがコンパイラのルールと衝突し始め、これが内部アーキテクチャの全面的な書き直しの直接的なきっかけとなりました。
  - 主要機能: すべての機能が「opt-in」方式に変わりました。ソート・フィルター・ページネーションといった機能を`tableFeatures()`で明示的に登録して初めて、コードと型がテーブルに含まれます。状態管理はTanStack Storeベースに移され、購読単位のきめ細かい再レンダリング制御が可能になり、row・column・cellのAPIが共有プロトタイプに載ることで、大容量テーブルでメモリを大きく節約します(一部シナリオでは最大約90%)。
  - コード例:
```js
    import {
      columnFilteringFeature,
      rowSortingFeature,
      rowPaginationFeature,
      tableFeatures,
      useTable,
    } from '@tanstack/react-table'

    // 必要な機能だけ登録 → 残りのコードはバンドルから除外(tree-shaking)
    const features = tableFeatures({
      columnFilteringFeature,
      rowSortingFeature,
      rowPaginationFeature,
    })

    function Table() {
      const table = useTable({ features, columns, data })
      // ... ヘッドレスレンダリングはv8と同じモデル
    }
```
  - 実務での活用: ページネーションだけが必要なテーブルは、フィルターやグルーピングのコードをまったく含めません。半分ほどの機能しか使わないアプリなら、残りの半分を出荷しなくて済むため、管理者ダッシュボードやSaaSのデータグリッドのように、画面ごとに必要な機能が異なる場所で有利です。
  - 注意事項: 潜在的な総バンドルサイズは、v8の約14kBからv9の約25kBに増えました。つまり`stockFeatures`で全機能を一度に使うとかえって大きくなるため、個別の機能を一つずつimportしてこそtree-shakingの恩恵を得られます。機能オブジェクトはコンポーネントの外側に静的に定義することが推奨されます。
- **[Let's Make the Worst htmx Ever](https://zserge.com/posts/worst-htmx-ever/)** (出典: *JavaScript Weekly #797*)
  - 背景: Serge Zaitsevが「worst React」「worst Vue」に続き、今回はhtmxの本質を根本から再実装します。5千行におよぶ単一ファイルで悪名高いhtmxが実際に何をしているのかを、自ら作ってみながら理解しようという趣旨です。
  - 主要機能: 著者はhtmxのエッセンスを「SSS」と要約します。すなわち、要素をスキャンし(scan) → リクエストを送り(send) → レスポンスで置き換える(swap)。この3つさえあればhtmxの骨格が完成し、残りの機能(ブースティング、インジケーター、確認ダイアログなど)は、コアに手を加えないイベントベースのプラグインとして付け足します。
  - コード例:
```js
    // x-get属性をスキャン(scan)し、クリック時にfetch(send)後、レスポンスで置き換え(swap)
    document.querySelectorAll('[x-get]').forEach(el => {
      el.addEventListener('click', async (e) => {
        e.preventDefault()
        const res = await fetch(el.getAttribute('x-get'))
        el.outerHTML = await res.text() // これがhtmxの核心となる10行
      })
    })
```
  - 実務での活用: `beforeSend`・`afterSwap`のようなカスタムイベントを公開すれば、確認ダイアログ・スピナー・履歴の更新といった機能を、それぞれ十数行の独立したプラグインとして実装できます。フレームワークの「拡張ポイント」をどう設計すればコアを薄く保てるのかについての、良い教材です。
  - 注意事項: 著者自身も認めているように、失敗した`fetch()`やnon-2XXレスポンスの処理、プロミスベースのキャンセル、ビュートランジションの待機などは欠けているため、実際のhtmxを代替することはできません。あくまでも「動作原理の学習用」として捉えるべきです。

## 2. 🛠️ ツール & ライブラリ

## ✍️ おわりに

今週のリリースを貫く一つの流れは、「必要なだけ載せる」という哲学でした。TanStack Table v9が機能をopt-inへと転換したこと、htmxの本質を40行に還元して残りをプラグインへと追い出した実験、そしてBase UIのようなアンスタイルドライブラリの広がりまで、フレームワークの重心が「すべてを備えたデフォルト」から「明示的に選ぶ最小限のコア」へと移りつつある、という印象を受けます。コアを薄く保ち、拡張ポイントをうまく設計することが、結局はバンドルサイズと保守性を同時に手にする鍵になるようです。

他方で`keyv`・`cacheable`のサプライチェーン攻撃は、私たちがどれだけ良いアーキテクチャを組んでも、それを出荷するパイプラインが破られれば意味がない、という事実をあらためて突きつけます。staged/trusted publishingのようなデプロイの衛生がもはや選択肢ではないという点、そしてSmashingが指摘したように、AIが作ってくれたUIのアクセシビリティを私たち自身で検証しなければならないという点 —— 結局「生成」よりも「検証と信頼」が、今週の本当のテーマだったのかもしれません。
