## 🔥 今週の主要テーマ

今週は、AIエージェントがコードを読み書きする時代に合わせて、ツールや設計が再編されていく様子が目立ちました。Lovableの、RustベースでVite互換の開発サーバーOJ、エージェントが違反の理由を理解できるよう支援する@shadcn/lint、デッドコードを素早く検出するFallowが代表例です。Safari 27やReact 19.3といったプラットフォームのアップデート、Tailwind LabsのShopify参画のニュースも続きました。さらにIE時代のCSSハックの回顧や、行の長さ・行の高さといったタイポグラフィの基本まで加わり、フロントエンドの過去と現在をあわせて振り返る一週間でした。

## 1. 🔍 深掘り
- **[OJ: A Rust-Native, Vite-Compatible Dev Server](https://lovable.dev/blog/faster-previews-oj)** (出典: *React Status #491*)
	- 背景: Lovableは1日に約100万個のサンドボックスで、プレビューを一つずつ立ち上げては落とす運用をしています。Viteは、開発者1人がノートPC1台で使う状況を想定した設計です。そのため、インスタンスごとにJavaScriptランタイムとツールチェーン、多くのメモリが付随し、そのコストがコールドスタートの遅延やウォームサンドボックスの負担として積み重なっていました。
	- 主な機能: OJはViteのようにアプリを実行する単一のRustバイナリです。既存の`vite.config.ts`(または`oj.config.ts`)を読み込み、実際のViteプラグインを互換ブリッジ経由で実行します。React Fast RefreshやTanStack Startのようにアプリが依存する部分はRustで再実装し、RolldownとOxcの上に構築しました。ファイルウォッチャーからWebSocketまですべてRustで、プラグインやサーバーコードがJavaScriptを必要とするときだけ小さなNodeサイドカーを起動します。エージェントによる編集も考慮しています。ファイルウォッチャー、モジュールグラフ、コンパイラ、HMRを一つの同期されたパイプラインにまとめ、エージェントが複数のファイルを一度に書き込んでも、一つの一貫した更新にまとめて反映します。
	- 数値: コンポーネント10,000個の合成アプリで、コールドスタートはOJが1.2秒、Viteが4.9秒、メモリは約115MB対1.5GB以上でした。Excalidrawは約0.8秒対約2.3秒、288MB対2.4GBでした。実際のLovableプレビューを使った実験では、ロード完了までの中央値が17.4秒から8.0秒に、サンドボックスの確保時間が14.5秒から3.0秒に短縮されました。
	- 実務での活用: プレビューやサンドボックスを大量に立ち上げる環境や、エージェントが複数のファイルを連続で書き込むワークフローで意味があります。一般的なプロジェクトでは今すぐViteを置き換える必要はなく、OJはLovableのプレビューに小さな割合から段階的に適用している段階です。
	- 注意事項: オープンソースですが、まだ実験的です。著者も、速度の数値が完全に同一条件での比較ではないと述べています。Vite側の計測には`vite-plugin-checker`(tscで型エラーをオーバーレイ表示)が含まれており、OJはこのプラグインをまだホストしていません。
- **[CSS Curiosities of the Past](https://vale.rocks/posts/css-relics)** (出典: *Frontend Focus #758*)
	![CSS Curiosities of the Past](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/k6lzihdml7pitxrpadxq.jpg)
	- 背景: ブラウザが一つの標準に忠実ではなかった時代、特にInternet Explorerの非標準な実装に対応するために書かれていた、CSSの構文・パースバグ・ハックをまとめたエッセイです。タイトルの「CSSがJavaScriptを実行していた時代」は、この記事に登場するCSS Expressionsを指しています。
	- 主な機能: 代表的な事例は次のとおりです。
		- star hack: `*`を前置したプロパティをIE7以下のみ有効として処理し、`_`を前置したプロパティをIE6のみ有効として処理しました。
		- clearfixの`zoom: 1`: IEの`hasLayout`フラグを有効にするための回避策でした。
		- CSS Expressions: IE5で導入され、IE8で終了しました。
		- DirectXベースの`filter`: `-ms-filter`がIE10で削除されるまで使われていました。
		- HTML Components: `behavior: url(...)`でスクリプトを紐付ける方式でした。
		- Tantek Çelikのbox model hack: `voice-family`のパーサーバグを利用していました。
	- コード例:
```css
		*width: 250px;   /* IE7以下のみ有効として扱う (star hack) */
		_width: 200px;   /* IE6のみ有効として扱う */
		top: expression(eval(document.documentElement.scrollTop)); /* CSS内でJSを実行 */
		filter: alpha(opacity=50);   /* IE専用のfilter */
```
	- 実務での活用: 古いスタイルシートでこのような宣言に出会ったとき、何のためのコードだったのかを読み解き、安全に削除できるかどうかを判断するのに使えます。
	- 注意事項: CSS Expressionsは、レンダリング、リサイズ、スクロール、マウス移動のたびに再評価されるため、パフォーマンスへの負荷が大きかったと記事は説明しています。ほとんどが標準ではないので、現在のコードに導入する対象ではなく、歴史資料として読むのが適切です。

## 2. 🛠️ ツール & ライブラリ
- **[@shadcn/lint : An Agent-First Linter for Tailwind Design Systems](https://github.com/shadcn-ui/lint)** (出典: *React Status #491*)
	![@shadcn/lint : An Agent-First Linter for Tailwind Design Systems](https://res.cloudinary.com/cpress/image/upload/w_1280,e_sharpen:60,q_auto/afaokicwppgsd63qh1c5.jpg)
	+ 概要: 型で「Buttonのpaddingは禁止」と制限することはできますが、エラーメッセージは禁止されているという事実しか伝えず、サイズをどう決めればよいかは教えてくれません。@shadcn/lintは、コンポーネントが受け取れるTailwindクラスをあらかじめ宣言しておき、違反すると、プロジェクトのコンポーネント・variant・テーマをもとに代替案を提示するESLint/Oxlintプラグインです。Tailwind v4のプロジェクトで使用し、shadcn/uiは必須ではありません。
	+ 使い方: Oxlintの設定(`.oxlintrc.json`)の例です。ESLintも同じsettingsとrulesを使います。
```json
		{
		  "jsPlugins": ["@shadcn/lint"],
		  "settings": { "shadcn": { "ui": "@workspace/ui/components" } },
		  "rules": { "shadcn/no-restyle": ["error", { "allow": ["layout"] }] }
		}
```
	+ 実践チップ: `allow: ["layout"]`は、レイアウト系のクラスのみ許可するという意味です。モノレポでは、コンポーネントを定義するディレクトリ(`packages/ui/src/components/**`など)でoverrideを使ってルールをオフにしておきます。既存のプロジェクトでは、ドキュメントの導入ガイドどおり、警告から始めてルールを一つずつ増やしていくのが安全です。
- **[Fallow: Codebase Intelligence for TypeScript and JavaScript](https://docs.fallow.tools/)** (出典: *JavaScript Weekly #802*)
	+ 概要: エージェントが作ったコードは整理されないまま溜まりやすく、「このexportは本当に使われていないのか」といった判断は、ファイル単体ではなくimport/exportグラフ全体を見る必要があります。FallowはこれをこなすRustバイナリです。未使用コード、重複、循環依存、複雑度のホットスポット、アーキテクチャ境界の違反を検出し、0〜100点のhealth scoreも算出します。基本の分析はNode.jsやTypeScriptコンパイラに依存せず、フレームワークプラグインがエントリーポイントを自動検出するため、初回実行時に設定は不要です。
	+ 使い方:
```bash
		npx fallow dead-code
		npx fallow health --score --hotspots --targets
		npx fallow dead-code --unused-class-members --type-aware --format json --quiet
```
	+ 実践チップ: 既存のコードベースでは`fallow audit`が便利です。変更によって新たに生じたfindingにのみ失敗を設定するため、レガシーな負債が原因で初日からCIが止まることがありません。既存のfindingは`--save-baseline`、`--baseline`で切り離します。エイリアス・re-export・パッケージをまたぐ正確なシンボル識別が必要なリファクタリングには、`--type-aware`を付けます。

## 3. 📝 おすすめ記事 & チップ
- **[From 1,256ms to 96ms: Fixing INP in a Massive React Dropdown](https://dev.to/subito/from-1256ms-to-96ms-fixing-inp-in-a-massive-react-dropdown-16l7)** (出典: *React Status #491*)
	![From 1,256ms to 96ms: Fixing INP in a Massive React Dropdown](https://media2.dev.to/dynamic/image/width=1000,height=420,fit=cover,gravity=auto,format=auto/https%3A%2F%2Fdev-to-uploads.s3.us-east-2.amazonaws.com%2Fuploads%2Farticles%2F3foxjs5p3218h59s9c3g.jpeg)
	+ 背景: Subitoのデザインシステムに含まれるMultiSelectは、ほとんどの項目が12個前後のため、即座に開いていました。ところが、ブランドフィルターの約1,175個のオプションでは、4倍のCPUスロットリングをかけたモバイル環境で、開くときのINPが1,256msとなり「poor」評価でした。画面には6行ほどしか見えないのに、オプションコンポーネント約1,175個を1回の同期コミットでマウントしたことが原因でした。
	+ 主要なインサイト: 約90行の`useVirtualScroll`フックで、表示されている行と上下5個のバッファ(`OVERSCAN`)だけをレンダリングし、INPを96msに、`role="option"`のDOMノードを13個に減らしました。すべての行の高さが同じという前提のおかげで、コードをここまで小さくできました。
	+ コード例:
```js
		const totalHeight = totalCount * itemHeight;
		const startIdx = Math.max(0, Math.floor(scrollTop / itemHeight) - OVERSCAN);
		const endIdx = Math.min(totalCount, Math.ceil((scrollTop + maxHeight) / itemHeight) + OVERSCAN);
		const offsetTop = startIdx * itemHeight;
```
	+ 解説: コピーする前に行の高さの種類を数えてみる方法もあわせて示しています。値が一つでなければ、行を均一にするか、TanStack Virtualやreact-virtuosoのようなライブラリを使うよう案内しています。仮想化すると画面外の項目がDOMから外れ、ブラウザ標準の検索(Ctrl+F)にヒットしなくなるというアクセシビリティ上のトレードオフも隠さずに述べており、そのまま取り入れやすい記事です。
- **[Better Icon and Label Alignment](https://ishadeed.com/article/aligning-list-icons/)** (出典: *Frontend Focus #758*)
	+ 背景: アイコン付きのリストでは、テキストが1行のときはアイコンが中央に揃いますが、複数行に折り返されると、中央揃えのアイコンは不自然に見えます。`align-items: start`に`translateY(3px)`のような固定値を指定する方法は、フォントサイズ、アイコンサイズ、コンテナ幅が変わると崩れます。
	+ 主要なインサイト: 1行目のline-height(`1lh`)とアイコンサイズの差を半分にした値をオフセットとして使います。そうすれば、3つの条件が変わっても揃いが保たれます。アイコンを`::before`の背景画像として入れる場合は、`flex-shrink: 0`、`aspect-ratio: 1`、`height: auto`を併用する必要があります。
	+ コード例:
```css
		.icon {
		  --offset: calc((1lh - var(--size)) / 2);
		  transform: translateY(var(--offset));
		}
```
	+ 解説: マジックナンバーを計算式に置き換えていく過程を、ステップごとのデモで見せてくれます。デザインシステムのリストコンポーネントにそのまま移せるパターンです。
- **[How To Set Text Properly](https://pimpmytype.com/line-length-line-height/)** (出典: *Smashing Newsletter #576*)
	![The Ideal Line Length And Line Height](https://mcusercontent.com/16b832d9ad4b28edf261f34df/images/c5958bb2-53dd-4532-2958-b2289757f04d.png)
	+ 背景: Oliver Schöndorferが、フォントサイズ、行の長さ、行の高さを「タイポグラフィの三位一体」としてまとめて解説したシリーズのうち、行の長さと行の高さの回です。リンク先の記事は2021年に書かれ、2022年に更新されたものです。
	+ 主要なインサイト: デスクトップの本文は、1行60〜80文字、行の高さ1.5〜1.6程度が出発点で、行が短いほど行の高さを下げられます。モバイルは1.3〜1.45、見出しは約1.1、UIコンポーネントは1.2〜1.3を提案しています。フォントを先に決めてから、サイズ、行の長さ、行の高さの順に調整することを勧めています。60〜80文字が読む速度で検証された数値ではないという点も指摘しています。
	+ コード例:
```css
		p {
		  max-width: 64ch;
		}
```
	+ 解説: `rem`基準では1remがおよそ2文字分の幅になるため、`max-width`を30〜40remに設定でき、`ch`単位を使えばフォントサイズを考慮する必要がありません。「正解の数字はない」という前提のもと、判断の基準を教えてくれる記事です。

## ✍️ おわりに

今週のニュースでもっとも目を引いたのは、ツールの利用者が人間からエージェントにまで広がっているという点でした。OJは、複数のファイルが一度に書き込まれる編集パターンを前提にHMRパイプラインを設計し直し、@shadcn/lintはエラーメッセージそのものを、エージェントが自分で修正できる形にしました。ルールを設けることよりも、違反したときにどう直せばよいかを伝えることのほうが重要になってきているという印象を受けました。

逆に、CSS Curiosities of the Pastを読むと、今では当たり前に使っている標準機能が、どれだけ多くの回避策の上に成り立っているかを改めて実感します。`lh`単位でアイコンの揃えを解く方法や、行の高さが同じという前提で90行の仮想スクロールを作ったINPの事例は、どちらも問題の前提を正確に絞り込み、小さな解決策を得たという共通点がありました。新しいツールが次々と登場する時期だからこそ、前提条件を先に確認する習慣がより価値を持つと思います。
